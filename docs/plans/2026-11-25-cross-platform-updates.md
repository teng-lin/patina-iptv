# Update discovery and installation for Android and desktop

Implementation proposal for [issue #213](https://github.com/teng-lin/patina-iptv/issues/213), revised November 26, 2026.

A viewer watching on a phone, tablet, TV or desktop should be able to check whether their installed copy of Patina has an update. On Android TV, the viewer should eventually be able to complete that update with the remote and reopen the same library.

| Delivery milestone | What viewers receive | Release decision |
| --- | --- | --- |
| 1. Manual discovery | **Check for updates** on Android phone, tablet and TV, Windows x64, macOS arm64 and Linux x86_64 | Ship when every listed app can identify its installed package, verify the feed and show the appropriate result. |
| 2. Direct Android installation | A signed APK upgrade, confirmed in Android’s system installer | Enable after touch and remote-only upgrade tests pass and the encrypted catalog reopens. |
| 3. Desktop installation | Signed installer handoff on Windows, a signed app update on macOS, and full AppImage replacement on Linux | Enable each route independently after its packaging, recovery and signing checks pass. DEB, RPM and pacman users continue through their package manager. |

Existing users need one manual upgrade to acquire the checker. Explain that step in the first release that includes it. Keep iOS, iPadOS, Tizen and store enrollment for later proposals.

## What happens when a viewer checks

Add **Settings → About → Check for updates** through the existing native Settings action flow. Show installed and offered versions, release notes, and the action the installed package supports. Distinguish “up to date” from a failed check and from a newer release with no compatible package. Use touch on phones and tablets, keyboard or mouse on desktop, and D-pad focus, Select and Back on TV. A TV without a browser should show a readable short address for manual instructions. When APK installation ships, completing the update on TV should require only the remote. [Settings rows and actions](../../crates/iptv-app/src/settings_view.rs) · [Available Settings actions](../../crates/iptv-app/src/settings_offer.rs)

The runtime owns an asynchronous check and its result. Keep eligibility a pure comparison of the installed build and verified release records. Host adapters handle network access, trusted storage, opening links and installer handoff. Keep verifier and platform dependencies outside the portable crates. Stamp distribution identity at packaging time. In particular, the Linux packages currently share a staged binary, so stamp each package separately or query its installed package ownership. An unknown or development build gets release information only. [Linux packaging](../../tools/ci/package-linux.sh)

Start with manual checks. A later opt-in daily check can run after startup and show one dismissible notice per eligible version outside active playback. Fetch the common metadata and select the package locally. Send no provider headers, playlist URLs, credentials, account or device identifiers. Document the update host and the ordinary IP address exposure in the privacy disclosure before enabling network checks. A failed check, denial, or unsupported version must leave the viewer free to continue.

## Release contract

Build the feed from the public assets the release workflow has verified. For example, v0.1.10 ships one dual-ARM APK for direct Android installs, a store-upload AAB, Windows x64 and macOS arm64 previews, and four Linux x86_64 formats. Only some of the files attached to a tag are viewer downloads. [v0.1.10 assets and signing notes](https://github.com/teng-lin/patina-iptv/releases/tag/v0.1.10) · [Release process](../release.md)

1. **Publish after verification.** Extend the successful production `verify-published` path to emit a release record from the bytes it verified. Record tag, commit, OS, supported architecture(s), OS floor, package format, distribution source, platform build version, signing status, notes URL, immutable asset URL, byte length and SHA-256. Allowlist installable formats. The APK is the Android download. The AAB, SBOMs and source archives have other consumers. Merge each verified package into the index independently so a partial release preserves earlier entries for other platforms. Reject a late promotion that would move a package to an older build. [Release workflow](../../.github/workflows/release.yml) · [Public artifact verifier](../../tools/ci/verify-public-release.py)
2. **Authenticate discovery and downloads.** Prototype TUF-on-CI and a native Rust verifier such as `tough` against the same synthetic signed repository on Android ARMv7/ARM64 and the three desktop targets. Embed the trusted root, persist verified metadata versions across restarts, and check expiry, compatibility, artifact length and hash before handoff. Host production metadata on a separate static deployment so a feed refresh cannot overwrite the existing privacy site. Record its stable URL, the offline root custodians and their signature threshold, then rehearse rotation and recovery before production signing. Keep rehearsal keys and URLs separate. Schedule metadata refreshes between releases. [TUF specification](https://theupdateframework.github.io/specification/latest/)
3. **Publish consistently.** Serialize promotions and refreshes, upload referenced metadata first, then advance the signed timestamp. Retries must converge on the same eligible packages. Verify the public result. Withdraw a bad target in newer metadata and issue a higher-version repair for devices already updated. Fail closed on a verification error and leave playback available.
4. **Start with one production track.** Keep publisher signing status distinct from release track. A Windows preview installer can accompany a stable Android release of the same version. Give it a clearly labeled release-notes link. Use a separate staging feed for trials. Defer public preview enrollment until there is a monotonic native build ordering across promotion and return to stable. Android’s current release tooling assigns one version code per numeric major.minor.patch. [Version stamping](../../tools/ci/version.py) · [Desktop signing policy](../../tools/ci/signing-policy.json)

## Installation milestones

| Installed package | First action | Gate for installation from Patina |
| --- | --- | --- |
| Direct Android APK on phone, tablet or TV | Show the compatible APK release. First installer milestone adds **Download and update**. | Build the install capability and permission into the direct APK only. Check the final APK and AAB manifests in CI. Download privately and verify length, digest, application ID, compatible signing identity and strictly higher version code. Handle per-source install permission, return from Settings, and Android’s confirmation screen. Reconcile the installed version after process replacement. Cancel or retry without an uninstall. [Android build](../../hosts/android/app/build.gradle.kts) · [PackageInstaller](https://developer.android.com/reference/android/content/pm/PackageInstaller) |
| Windows x64 per-user setup EXE | Open release notes with the unsigned-preview label while preview policy applies. | Verify the expected Authenticode publisher and the exact authorized EXE. After user confirmation and a safe exit, run the existing per-user Inno installer with its stable AppId. Exercise cancel, locked files and reopening the existing library as a standard user. [Installer recipe](../../tools/ci/windows-installer.iss) |
| macOS arm64 DMG | Open release notes with the preview signing status and manual replacement instructions. | Ship a Developer ID-signed, notarized app with Sparkle 2. Generate its signed appcast and archive from the same authorized release record. Ensure Sparkle installs only the selected build. Test upgrading from Applications, launching from a read-only DMG, cancellation and relaunch. Document the manual move to the first updater-enabled signed app. [Sparkle publishing](https://sparkle-project.org/documentation/publishing/) |
| Linux x86_64 AppImage | Link to the matching full AppImage. | For a writable installation, stage on the same filesystem, verify, set executable permissions and atomically replace after confirmation. Retain the previous file until successful launch. Offer a save location when replacement is unavailable. Test interrupted downloads, insufficient space, read-only paths and failed launch before enabling replacement. |
| Linux x86_64 DEB, RPM, pacman | For manually downloaded packages, link to the matching release asset and use the system package tool. For repository-managed installs, direct the viewer to their configured source when it offers the update. | Leave system file changes and privileges to the package manager. Never promise a repository version from GitHub availability alone. Test install-over-previous for all three formats. Creating package repositories is separate work. |

Checks and downloads may run during playback. Ask before leaving playback to install. Defer any handoff that can terminate an active recording until it finishes or the viewer explicitly stops it. Recheck at handoff, release application resources cleanly, and clean up incomplete downloads and abandoned installer sessions.

## Acceptance and rollout

- **Publisher and verifier.** In staging, publish Android alone and desktop alone, retry a promotion, deliver an older job late, and interrupt publication before advancing the timestamp. Verify each client still sees its newest compatible package. Test a missing asset, wrong architecture, bad hash, expired metadata, replay after restart, clock error and root rotation across skipped releases.
- **Android.** Issue #229 records a successful manual 0.1.5 → 0.1.6 APK upgrade on a Galaxy Tab A9+ and a Chromecast with Google TV. Use that as the baseline for the new in-app handoff. Exercise check, permission denial, return to Settings, confirm, cancel, retry and relaunch. Use a phone in portrait and landscape, a tablet, and a TV with only the remote. Use disposable `tab36` and `tv36` for UI coverage and run two successive production-signed APKs on representative ARM hardware. Verify preserved synthetic playlists, favorites, settings and access to the encrypted catalog. Record signer, package ID and both version codes for each tested upgrade. [Android validation](../android-validation.md) · [Prior APK upgrade report](https://github.com/teng-lin/patina-iptv/issues/229)
- **Desktop.** Test from two successive packaged builds through the normal About entry point on each OS. Record the signing status, install location and package format. Verify cancellation and recovery leave a launchable app, encrypted data remains readable, and an active recording survives a deferred update. Exercise a database migration in the upgrade pair before treating restoration of an older executable as recovery. Test the unsigned-preview discovery path independently of signed installation.
- **Delivery.** Land the staging verifier and publisher, then shared discovery, then direct Android installation. Desktop installation paths can proceed independently as each passes its signing and upgrade gates. Use existing test harnesses, the NSH revision in `nsh.rev`, the portable crate tests and Wasm builds, and the native app build. Before enabling each route, attach install-over-previous evidence for that package. Store migration, public preview tracks, background checking and delta downloads can follow independently.
