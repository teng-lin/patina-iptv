# Patina IPTV repository audit — 2026-11-13

**Overall assessment: 7.4/10.** Patina has a strong portable foundation, substantial behavioral tests, and unusually deliberate handling of provider input, storage encryption, and native packaging. The main weaknesses are application-layer coupling, gaps in Android premerge validation, release immutability, and a concrete custom-header privacy issue. These warrant targeted improvements rather than a redesign.

## Scope and method

- Audited revision: `8c259ee36fb45343f0ece3bfdd6f512b01b0f8e6` (workspace initially clean).
- Native Codex team: three parallel reviewers covering architecture/code quality; security/privacy; and testing/CI/distribution/documentation. The coordinating agent reviewed findings, inspected supporting code, and ran additional validation.
- Local NSH checkout: branch `tv-keys`, revision `4439410f78174fadacc35f6677b8a767ff206c90`, clean at inspection and matching the Linux/macOS CI pin.
- Scope: tracked source, tests, manifests, workflows, packaging scripts, and documentation. The repository contains 11 workspace crates and 405 tracked Rust files totaling approximately 118,520 lines, including tests. Counts describe size, not quality.
- Only synthetic fixtures and local test servers were used. No real providers were contacted, and no provider information from screenshots was inspected or reproduced.
- This is a sampled engineering audit, not a penetration test, exhaustive FFI review, dependency vulnerability certification, or certification of published packages. Current remote CI results and release artifacts were not inspected.

Scores are judgments on a 1–10 scale: 1–2 means foundational problems, 3–4 substantial weaknesses, 5–6 workable with significant gaps, 7–8 strong with concrete improvement areas, and 9–10 exceptional with convincing validation. The overall score is the equal-weight mean of the ten dimensions below; it is not a measured reliability percentage. Priority and confidence are separate from score.

Priorities describe recommended sequencing: **P1** before the next stable release, **P2** in the next focused improvement cycle, and **P3** subsequent hardening or polish. They are not CVSS severity ratings. No critical exploit was established in the sampled review.

## Findings and recommended actions

### A01 — Custom credential headers survive cross-origin playback requests

**Priority: P1 · Confidence: high, static control-flow evidence · Impact: credential confidentiality**

The M3U parser accepts arbitrary header names through Kodi properties and pipe syntax. Playback and redirect handling remove only five identity headers: `Authorization`, `Cookie`, `Proxy-Authorization`, `SN`, and `X-User-Agent`. Consequently, a playlist-supplied synthetic `X-Api-Key` or `X-Auth-Token` remains on a request when a redirect or adaptive-stream resource changes origin. An explicitly supplied `Referer` containing a credential can also survive; the code correctly avoids generating a new Referer automatically.

Evidence: [M3U header parsing](../../crates/iptv-providers/src/m3u/mod.rs#L252), [pipe headers](../../crates/iptv-providers/src/m3u/mod.rs#L460), [playback header removal](../../crates/iptv-net/src/playback.rs#L412), and [redirect header removal](../../crates/iptv-net/src/redirect.rs#L110). Existing [playback tests](../../crates/iptv-net/tests/it/playback.rs#L19) exercise the known identity names.

This requires an input containing a sensitive custom header and a cross-origin destination; it is not evidence that every playlist leaks credentials. Public-destination validation and TLS do not prevent disclosure to an otherwise valid public destination. No exploit reproduction was run.

**Action:** Scope arbitrary supplied headers to their original origin by default. Define a small, explicit cross-origin safe-header policy and deliberate exceptions where necessary. Add two-origin synthetic tests for redirects, HLS resources, and DASH resources, including custom secret headers and credential-bearing Referer values.

### A02 — Rust-only changes can skip the Android premerge build

**Priority: P1 · Confidence: high · Impact: platform regressions detected after merge**

The Android workflow's pull-request path filter covers manifests, host files, and packaging inputs but omits Rust source files. A change limited to an Android-specific Rust branch can therefore avoid an Android build. Desktop tests cannot compile those branches. Pushes to `master` do build Android, which mitigates the gap after merge.

Evidence: [Android change filter](../../.github/workflows/android.yml#L34), its [job condition](../../.github/workflows/android.yml#L59), and an example [Android-only Rust branch](../../crates/iptv-app/src/startup.rs#L66).

**Action:** Run an Android Rust compile check for Rust source changes. Expensive APK packaging can retain a narrower filter. Add a workflow-filter regression case showing that an Android-only `.rs` change selects the compile job.

### A03 — Documented screenshot provenance conflicts with the synthetic-only rule

**Priority: P1 · Confidence: high for the documentation conflict; image contents unverified · Impact: repository data governance**

The [README screenshot caption](../../README.md#L24) says the tablet screenshot contains a real provider's playlist. This conflicts with [AGENTS.md](../../AGENTS.md#L3) and the README's later claim that the repository has no real provider data. The audit did not open the screenshot or transcribe its content, so the confirmed finding is the declared provenance conflict, not an independently established credential leak.

**Action:** Replace the affected capture using generated fixtures and reconcile the caption and repository claims. Record the fixture-generation command beside future screenshots. Any review of prior artifacts should avoid reproducing provider content in issues or logs.

### A04 — Published release assets can be replaced under the same version

**Priority: P2 · Confidence: high · Impact: artifact identity and release trust**

The publish script accepts an existing release, uploads with `--clobber`, and marks it public without first checking whether it is already public. A workflow rerun can thus replace published package and checksum bytes under an unchanged version. This is an authorized-publisher failure mode, not evidence of an outsider obtaining release access.

Evidence: [release publication](../../.github/workflows/release.yml#L265). The [native runtime workflow](../../.github/workflows/mpv-runtime.yml#L102) already rejects an existing release.

**Action:** Refuse replacement of assets on a public release. Allow retries against a verified draft only, then publish once. Add checks for absent, draft, and public release states.

### A05 — Portable screen state depends on the native application and SQLite

**Priority: P2 · Confidence: high · Impact: architecture and reuse**

The playlist screen explicitly models pure state and effects, but imports `iptv_store_sqlite::SourceId`, app-owned `Playlist`, and `SourcePolicy`. Guide-source and guide-assignment state have similar dependencies. This weakens the stated “state lives in the core” direction, even though the existing core itself remains clean.

Evidence: [playlist state imports and effects](../../crates/iptv-app/src/playlists_view/state.rs#L9), [guide-source state](../../crates/iptv-app/src/epg_sources_view/state.rs#L8), and [guide-assignment state](../../crates/iptv-app/src/guide_assign_view/state.rs#L7).

**Action:** Extract portable identifiers, presentation data, and pure transitions into a domain crate. Keep database conversion and effect execution in native adapters. Move one screen at a time and preserve its behavior tests.

### A06 — Player-card logos are omitted for combined schedules

**Priority: P2 · Confidence: high, static control-flow evidence · Impact: visible feature inconsistency**

The player info card's logo helper downcasts the schedule to `EpgSchedule`; it returns `None` for `CombinedSchedule`, selecting the placeholder even when that channel has a logo. The `Schedule::channel_logo` interface already supports combined schedules.

Evidence: [concrete downcast](../../crates/iptv-app/src/player_panels/card.rs#L31), [placeholder fallback](../../crates/iptv-app/src/player_panels/card.rs#L185), and [combined implementation](../../crates/iptv-guide/src/combined.rs#L254). This was not reproduced through a running GUI.

**Action:** Use the schedule trait method while preserving URL validation. Add synthetic single-playlist and combined-playlist card cases. Review neighboring concrete downcasts for the same class of omission.

### A07 — Global ownership increases lifecycle and integration complexity

**Priority: P2 · Confidence: high for coupling; no race or data loss demonstrated · Impact: maintainability**

The application combines thread-local schedule state, global store services and epochs, and a large `Ui` collection of independently mutable signals. The integration harness explicitly explains that scenarios cannot share a process because of process-wide state and therefore launches separate child processes. Epoch checks and isolated tests are sensible protections, but they also show the cost of implicit ownership.

Evidence: [application state](../../crates/iptv-app/src/lib.rs#L168), [global store service](../../crates/iptv-app/src/store_service.rs#L24), and [test isolation rationale](../../crates/iptv-app/tests/app/isolated.rs#L3). `data.rs` and `data/stored.rs` each exceed 1,200 lines; their shared orchestration responsibilities matter more than their length alone.

**Action:** Incrementally introduce an owned app context with explicit lifecycle, storage, and clock dependencies. Group related state transitions. Retain process isolation where it protects native integrations, while making pure behavior testable without it.

### A08 — Device validation and production delivery remain uneven

**Priority: P2 · Confidence: high for workflow/documented limitations · Impact: release confidence**

Android CI performs JVM tests, lint, builds, and signature verification, but the inspected workflow has no tablet/TV runtime smoke execution. Persistent video surfaces, background/resume, and multiview transitions therefore depend on manual validation. The release guide acknowledges this requirement. Windows installers are documented as unsigned; macOS packaging can fall back to ad hoc signing when credentials are absent.

Evidence: [Android checks](../../.github/workflows/android.yml#L83), [device release checklist](../release.md#L84), [macOS signing branch](../../tools/ci/package-macos.sh#L6), and [Windows installation limitations](../../README.md#L115).

**Action:** Add repeatable synthetic device scenarios with retained per-release results, including guide/fullscreen/multiview transitions and background/resume. Make signing requirements explicit for stable releases, or clearly classify unsigned artifacts as previews. Headless tests should continue to complement device checks.

### A09 — Local builds and native package inputs are not fully reproducible

**Priority: P2 · Confidence: high · Impact: onboarding and artifact provenance**

The README clones the moving NSH `tv-keys` branch, whereas CI pins a commit. CI also installs current apt/Homebrew native dependencies. Locked Cargo graphs and checksum-pinned native downloads are valuable, but do not establish bit-for-bit reproducibility of all packages.

Evidence: [local NSH setup](../../README.md#L84), [CI NSH pin](../../.github/actions/setup/action.yml#L16), and [native dependency installation](../../.github/actions/setup/action.yml#L24).

**Action:** Share one NSH revision manifest between local setup and CI. Record native dependency versions and build-image identity with artifacts; use immutable build environments where practical. State the precise reproducibility guarantee rather than treating a lockfile as proof of identical binaries.

### A10 — Smaller hardening and documentation gaps

**Priority: P3 · Confidence: high for implementation facts; risk depends on environment**

- **Critical mpv options warn and continue.** Initialization sets `config=no`, `load-scripts=no`, `ytdl=no`, and `autoload-files=no`, but option-setting failures generally only log a warning. Fail initialization when a required restriction cannot be installed, retaining the explicit supported exception for scripting compiled out. No affected runtime was demonstrated, and the separate playback URL hook provides additional protection. Evidence: [options and helper](../../crates/iptv-app/src/mpv/handle.rs#L32).
- **Portable backups are intentionally plaintext.** This is documented and warned about in the UI, rather than a hidden violation of catalog encryption. Authenticated passphrase-protected exports would improve confidentiality after files leave app storage. Evidence: [backup security model](../security.md#L48), [export warning](../../crates/iptv-app/src/backup.rs#L709).
- **Release instructions lag the scripts.** Documentation still describes RPM/pacman checks as metadata checks and describes macOS as categorically unnotarized; scripts now perform distribution-container installation checks and support conditional notarization. Evidence: [release guidance](../release.md#L40), [Linux package checks](../../tools/ci/check-linux-packages.sh#L23), [conditional notarization](../../tools/ci/package-macos.sh#L29).
- **Localization and accessibility need demonstrated coverage.** Long-form help, some secondary/status text, pluralized counts, and date/time formatting remain English. Labels and font controls exist, but this audit did not test TalkBack/VoiceOver traversal or large-text clipping. Complete prioritized translation paths and retain assistive-technology smoke results. Evidence: [declared localization coverage](../localization.md#L14), [control labels](../../crates/iptv-app/src/ui_kit.rs#L24), [text scaling](../../crates/iptv-app/src/scale.rs#L75).

## Strengths to preserve

1. **Portable domain design.** `iptv-core` has no dependencies and forbids unsafe code. The import transport supports asynchronous streamed bodies without forcing `Send` futures. Native IO stays in adapters. See [core manifest](../../crates/iptv-core/Cargo.toml), [core safety policy](../../crates/iptv-core/src/lib.rs#L1), and [Fetch interface](../../crates/iptv-import/src/fetch.rs#L1).
2. **Identity-based navigation and persistent video layout.** List restoration captures channel/list identities, and the video component changes reactive geometry. These match important project invariants. Actual Android surface survival was not exercised here. See [focus restoration](../../crates/iptv-app/src/lists.rs#L75) and [video geometry](../../crates/iptv-app/src/video.rs#L95).
3. **Defense beyond superficial encryption.** SQLCipher covers catalog and staging data, production key-broker failure closes storage, and test-key injection is gated behind a nondefault feature. Restore validates archives, schema, integrity, and foreign keys before activation. See [encryption](../../crates/iptv-store-sqlite/src/encryption.rs#L11), [credential entry points](../../crates/iptv-app/src/credential_key.rs#L19), and [restore validation](../../crates/iptv-store-sqlite/src/backup.rs#L146).
4. **Careful untrusted-network handling.** Public-content address validation, vetted DNS results, HTTPS downgrade refusal, capability-bearing loopback playback, and bounded manifests/connections reduce substantial attack surface. A01 is a specific gap within this otherwise strong design. See [public resolver](../../crates/iptv-net/src/public_resolver.rs#L9) and [playback transport](../../crates/iptv-net/src/playback.rs#L28).
5. **Tests target behavior and failure modes.** Examples include historical schema migrations, parser chunking properties, synthetic real-mpv playback, encryption/wrong-key behavior, and isolated complete-app scenarios. CI also schedules parser fuzzing and large-catalog stress. See [migration tests](../../crates/iptv-store-sqlite/tests/it/migrations.rs#L1), [parser properties](../../crates/iptv-import/tests/it/parser_properties.rs#L7), [native player tests](../../crates/iptv-app/src/mpv/tests.rs#L1), and [stress workflow](../../.github/workflows/import-stress.yml).
6. **Performance has explicit constraints.** Tests bound guide mount/layout work and measure a 50 ms input budget under real SQLite writer contention. Refresh workers and image queues are bounded; programme search documents its compact index. See [scroll-cost assertions](../../crates/iptv-app/tests/app/guide_scroll_cost.rs#L217), [storage-contention test](../../crates/iptv-app/tests/app/store_latency.rs#L63), [refresh workers](../../crates/iptv-app/src/data/workers.rs#L7), and [search index](../../crates/iptv-search/src/programmes.rs#L1).
7. **Packaging is treated as engineering work.** Pinned actions, generated-workspace lock enforcement, package smoke checks, separate signing steps, dependency notices, and retained Windows native sources are substantial strengths. See [check entry point](../../tools/check.sh), [locked Cargo wrapper](../../tools/ci/locked-cargo.py#L25), and [native runtime workflow](../../.github/workflows/mpv-runtime.yml).

## Validation performed

The audit ran on Linux x86_64 using system Rust/Cargo 1.99.1. Results below distinguish executed checks from inspected CI definitions.

| Check | Result |
| --- | --- |

| `cargo build -p iptv-core --target wasm32-unknown-unknown` | **Blocked by environment:** E0463, target standard library unavailable. `rustup` is not installed on this host. This does not establish a source portability defect. |
| `cargo build -p iptv-app` | **Passed** on the local Linux/NSH environment. |
| Non-app workspace crate tests, excluding the separately tested core | **Passed:** 593 tests/doctests passed; 3 tests and 2 doctests ignored; no failures. |
| `cargo test --locked -p iptv-app --features test-support --quiet` | **Passed:** 209 unit tests and 58 integration scenarios; 1 latency scenario ignored by the normal suite; no failures. |
| Separately executed SQLite-contention latency scenario | **Passed:** the 50 ms key-to-mounted-frame assertion held while a real database writer lock was held. This is a headless measurement, not device frame timing. |
| Packaging/version Python helper tests | **48 passed:** versioning 6; package lock 2; iOS entitlements 3; signing-input unpacking 4; NSH cache identity 14; native source preparation 13; native runtime packaging 6. Executed by the testing/distribution reviewer. |
| `python3 tools/ci/check-package-lock.py` | **Passed:** source/runner dependency identities agree. |
| Windows patch regression helper | **Blocked by environment:** `powershell.exe` unavailable. |

The non-app test command was:

```sh
cargo test --locked -p iptv-nav -p iptv-settings -p iptv-epg \
  -p iptv-providers -p iptv-guide -p iptv-import -p iptv-net \
  -p iptv-store-sqlite -p iptv-search --quiet
```

The latency scenario was run separately, after the other suites finished:

```sh
cargo test --locked -p iptv-app --features test-support --quiet --test app \
  store_latency::guide_input_stays_under_budget_while_the_database_writer_is_locked \
  -- --ignored --exact
```

The app suite was run without `IPTV_REQUIRE_PLAYER_TESTS=1`; its harness can return early when native player prerequisites are unavailable. The passing suite alone therefore does not certify that every native rendering path ran. The three ignored non-app tests cover larger/manual performance work and schema-snapshot generation; two illustrative SQLite doctests are also ignored.

The full `tools/check.sh` pipeline (including Clippy and dependency policy checks), new fuzz campaigns, package builds/installations, current advisory database refresh, OS credential-broker integration, screen-reader checks, and tab36/tv36 execution were not completed during this audit. No Android implementation was changed. In particular, inspecting a test or workflow is not a claim that it passed, and an application build is not proof of runtime behavior on every platform.

## Recommended sequence

1. Address A01's credential-header policy, A02's Android compile gate, and A03's screenshot provenance conflict.
2. Make public releases immutable; repair the combined-schedule logo path; establish repeatable synthetic device smoke evidence.
3. Extract screen state incrementally, consolidate app ownership, and align local dependency setup with CI.
4. Complete production signing policy, optional encrypted exports, release documentation, and accessibility/localization validation.

The audit changes documentation only. Findings are recommendations; no implementation fixes, release publication, or repository-history changes were performed.
