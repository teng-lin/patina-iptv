# Patina IPTV repository audit — 2026-11-14

**Overall assessment: 8.3/10, up from 7.4/10 in the previous Codex audit.** The intervening work materially improves the repository: portable library state, an owned application runtime, independent storage read/write lanes, stricter transport policies, Android checks, and release provenance are implemented and protected by tests. The main remaining work is narrower: two confirmed edge-case defects, stronger device lifecycle validation, and completion of signing and accessibility evidence.

This review found no new P1 issue in the sampled code. That is a statement about the evidence gathered, not a guarantee that the repository is free of serious defects.

## Confirmed defects

### B01 — Supplied `Origin` values bypass the new value-sanitization policy

**P2 · High confidence · Function-level reproduction and static call-path evidence**

The allowlist retains `Origin` because the comment assumes it contains no path or query. That property is not enforced for playlist-supplied values. The M3U pipe parser explicitly accepts an arbitrary `Origin` string, and `cross_origin::restrict` leaves it unchanged. A synthetic value such as `https://portal.example.test/watch?token=synthetic-secret` therefore retains its path and token when the destination changes origin.

Evidence: [M3U pipe parsing](../../crates/iptv-providers/src/m3u/mod.rs#L460), [allowlist and filtering](../../crates/iptv-net/src/cross_origin.rs#L26), [redirect caller](../../crates/iptv-net/src/redirect.rs#L104), and [playback caller](../../crates/iptv-net/src/playback.rs#L418). Existing tests cover a well-formed origin, not this malformed value.

**Reproduction:** A temporary Rust executable imported the repository's actual `cross_origin.rs`, inserted the synthetic value into a `HeaderMap`, called `restrict` between two different synthetic HTTPS origins, and asserted that the original value remained. It passed. No network request or real credential was involved.

This requires a supplied header containing sensitive data; normal, well-formed `Origin` values do not exhibit the path/query leak. It is narrower than the previous arbitrary-header finding and is not evidence of automatic leakage from every source.

**Action:** Validate or normalize `Origin` before allowing it across origins. Define handling for `null`, duplicate values, userinfo, non-HTTP schemes, paths, queries, and malformed input. Extend the synthetic redirect and adaptive-resource tests to cover those cases while retaining same-origin compatibility.

### B02 — Retrying a draft ignores freshly generated signing notices

**P2 · High confidence · Reproduced with the repository's local GitHub CLI stub**

`publish(directory, tag, notes)` consumes `notes` only when creating an absent release. For an existing draft, it uploads the current files and publishes without updating the body. An interrupted draft with older or missing preview wording can therefore become public with notes that do not describe the current signing records. This can occur when signing configuration changes between attempts, or when a draft was prepared with different notes.

Evidence: [publisher](../../tools/ci/publish-release.py#L142), [fresh notes generated by the workflow](../../.github/workflows/release.yml#L438), and [existing retry tests](../../tools/ci/test-publish-release.py#L111).

**Reproduction:** Using `Publishing` from `test-publish-release.py`, created synthetic packages and checksums, seeded a draft with older notes, and invoked the real publish script with a replacement unsigned-package notice. The stub observed `view, upload, view, edit`; publication succeeded and the old notes remained. No GitHub write occurred.

The asset checksums and public-release refusal are unaffected. This is a release-description consistency defect, not an artifact-integrity bypass.

**Action:** Reconcile the generated signing notice on every draft retry before publication, preserving intended release prose. Test both unsigned-to-signed and signed-to-unsigned transitions, including removal of an obsolete preview notice.

## Remaining engineering gaps

### B03 — Android smoke coverage does not yet establish process-death recovery

**P2 · High confidence for test scope · Validation gap, not a demonstrated device bug**

The new smoke script covers first import, playback, fullscreen, multiview, and background/resume. It explicitly requires the app process to remain alive while backgrounded. Consequently, passing it does not establish recovery after process death, activity recreation, an interrupted restore, or refresh while playback is active. Those are relevant to the new runtime, captured worker context, and queued writes.

Evidence: [background/resume sequence](../../tools/ci/android-smoke.sh#L163). The [PR path filter](../../.github/workflows/android-smoke.yml#L3) also omits portable crates such as `iptv-core`, `iptv-import`, and `iptv-library`; changes confined there get Android compile coverage but may wait for the scheduled smoke run for behavior coverage. The workflow explicitly documents that it is not a required check.

**Action:** Add synthetic recovery cases with persisted-state assertions: kill and reopen after accepted writes, recreate the activity, refresh while playing, and interrupt/recover a restore. Broaden behavioral triggering to relevant portable crates, or document a deliberate pre-release gate covering them. Retain a passing tablet/TV run against the release candidate. No new tab36/tv36 run was performed in this documentation-only audit.

### B04 — Runtime ownership is clearer, but its API remains easy to couple to

**P3 · High confidence · Maintainability cost; no new race or data-loss claim**

The runtime is a meaningful architectural improvement. However, many state fields remain `pub(crate)`, and callers reach them through `crate::runtime()`, a thread-local application handle. The isolation guarantees depend on context wrappers at asynchronous boundaries. The architecture tests reject known imports by scanning source text; they do not provide a compiler-enforced crate boundary or prevent shell code from changing runtime internals directly.

Evidence: [runtime fields](../../crates/iptv-app/src/runtime/mod.rs#L42), [ambient handle and poll scoping](../../crates/iptv-app/src/lib.rs#L394), [architecture checks](../../crates/iptv-app/tests/app/architecture.rs#L117), and a [shell-side runtime-state update](../../crates/iptv-app/src/data/stored.rs#L43).

The runtime contains approximately 8,793 source lines including inline tests, still inside `iptv-app`. The [coverage command](../../tools/ci/coverage.sh#L11) excludes the app, so the new library coverage report also excludes these runtime branches. Runtime tests do run in the app suite; absence from coverage measurement does not mean absence of tests.

**Action:** Gradually make fields private and move transitions behind methods or named commands. Measure runtime branch coverage and keep owner-retirement/failure-path tests. Extract a separate native runtime crate when it gives a concrete build or testing benefit; do not reopen the whole refactor merely to move files. Process isolation of NSH/player scenarios remains reasonable.

### B05 — Stable desktop distribution still needs demonstrated platform signing

**P2 for stable distribution · Operational completion gap**

The workflow has signing/notarization paths, verifies Windows signatures, and emits signing-status records. The README still describes macOS and Windows downloads as previews until signing is configured. That is an honest and appropriate policy; implementation support alone is not evidence that released packages are signed.

Evidence: [preview policy](../../README.md#L90), [Windows signing and verification](../../.github/workflows/release.yml#L87), and [release signing jobs](../../.github/workflows/release.yml#L299).

**Action:** Keep the preview classification until an actual candidate passes signature/notarization verification and clean-machine installation checks. Record the result alongside the release. This audit did not inspect secrets or infer their current availability. Also retain the distinction between pinned inputs, build provenance, and proven byte-for-byte reproducibility; the latter was not measured.

### B06 — Translation breadth exceeds demonstrated accessibility coverage

**P3 · High confidence for documented translation gaps; accessibility unverified**

Eleven interface languages, translated accessibility labels, scalable text, and identity-based navigation are valuable foundations. The project still documents English-only help, secondary/status text, pluralized counts, and date/time formatting. Headless scenarios exercise language changes and input behavior but do not establish usable TalkBack/VoiceOver traversal, spoken state changes, or absence of large-text clipping.

Evidence: [translation coverage](../localization.md#L13), [UI control labels](../../crates/iptv-app/src/ui_kit.rs), and [language scenarios](../../crates/iptv-app/tests/app/interface_languages.rs).

**Action:** Prioritize common errors and recovery flows, then locale-aware counts/time formatting. Add a repeatable assistive-technology and large-text checklist covering guide navigation, modal focus restoration, settings, and player controls, with synthetic device evidence.

Plaintext portable backups remain an explicit design limitation rather than a newly discovered defect. The warning and [security documentation](../security.md#L48) explain it. Authenticated, passphrase-protected exports would be a useful future feature; their absence does not negate encryption of normal app storage.

## Recommended order

1. Validate cross-origin `Origin` values and update signing notices when retrying drafts, with the focused regression cases described above.
2. Extend Android smoke coverage to process recreation and restore/refresh interactions, and capture release-candidate results on tablet and TV.
3. Verify desktop signing on actual artifacts before changing preview status.
4. Tighten runtime encapsulation incrementally, include its branches in coverage measurement, and complete prioritized accessibility/localization work.

This audit adds documentation only. It makes no product fixes, changes to releases, or repository-history edits.
